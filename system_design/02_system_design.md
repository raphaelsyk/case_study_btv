## Suggested System design
- Separation of concerns: The system has three core components, that should be decoupled: 1. A Data transformation pipeline taking the PDFs and transforming it into structured data model (e.g. json), 2. a data storage system for storing that data (e.g. a folder or a document database), 3. An Analyzer module performing that performs the AI trend/sentiment analysis
- For the design of the data model, see the file  '03_system_design_data_model.md'


## System design Decisions
### Core Components
1. **Data Transformation Pipeline**: converts a raw earnings-call PDF into the structured data model (see `03_system_design_data_model.md`). Fully topic-agnostic — it extracts the complete transcript (call identity, participants, all speaker-tagged turns) independent of any downstream analysis topic (AI or otherwise), so the same pipeline serves future report generators beyond the AI use case.
2. **Data Storage**: persists the structured transcripts produced by the pipeline and is read by the Analyzer. Decoupled behind a storage interface so the backing technology can change without touching the other components.
3. **Analyzer Module**: consumes structured transcripts from storage to produce topic-specific reports (e.g. the AI-discussion-over-time report). Owns topic filtering, cross-quarter synthesis, and citation verification (checking that generated statements are grounded in the stored source text) — none of this lives in the transformation pipeline. Detailed design deferred to a later session.

### Data Transformation Pipeline
- **Extraction (PDF → raw page text)**: use `docling`, run **per page** (`DocumentConverter.convert(path, page_range=(n, n))`, docling supports this natively — no separate PDF-splitting library needed). This guarantees every extracted text block carries an unambiguous, single page number, which whole-document conversion does not: observed on a Microsoft transcript that docling's whole-document run merges several pages — and even several different speakers — into one text block, because that source has no paragraph-per-turn formatting to key off of. Docling reads the embedded text layer directly (documents are digitally native, not scans), so extraction fidelity is not the bottleneck — turn/page segmentation is.
- **Structuring (raw page text → structured schema)**: use an LLM (Gemini, see Tech stack) to turn the page-tagged raw text into the structured schema — participants, call identity, and speaker-tagged turns. Pages are delimited inline as `<page N>...</page N>` in the text handed to the model, so page attribution survives into its output. Chosen over per-source deterministic parsers because earnings-call PDF layouts vary significantly by source/vendor (observed concretely across BAC/JPM/NVDA/MSFT samples) and a hand-written parser per template does not scale to the extensibility requirement (new companies, new vendors). Parsing/structuring logic is dispatched by **detected document structure**, not by company identity, so a new company using an already-known vendor template needs no new code.
- **Two structuring calls, not one**: (a) call identity + participants, over just the first page(s); (b) full turn segmentation (speaker, pages, text, section) over the whole page-tagged document. Keeps each call's output bounded and schema-simple rather than one large, failure-prone JSON response. Participant detection in call (a) is **optional** — BAC and NVDA list a participant roster up front, but JPMorgan and Microsoft only reveal external/analyst participants by them speaking in the Q&A, so call (a) may legitimately return an empty or partial list for those. Call (b)'s speaker tag is not just a name: the model also extracts role/company when stated inline next to the speaker label (e.g. JPM's "Christopher McGratty / Analyst, Keefe, Bruyette & Woods, Inc.", MSFT's "KEITH WEISS, Morgan Stanley:"), since that's the only place this information exists for speakers who never appear in an upfront roster. After call (b), the participants list is reconciled: any speaker present in the turns but missing from call (a)'s roster is added, carrying whatever role/company call (b) recovered — a **union, not a replace**, since call (a) may list attendees (e.g. a corporate secretary) who are present but never speak.
- A Gemini call failing or returning invalid output for one document skips/logs that document; it does not halt processing of the rest of the corpus.
- **Build order**: implement the general LLM-based structuring path first, since it works across all observed templates immediately. A deterministic fast-path (e.g. regex/heading-based parsing for the more regular vendor templates) is a possible later optimization for cost/latency/determinism, not a prerequisite.
- **Grounding check**: because extraction (docling) and structuring (LLM) are separate steps using independent techniques, each structured turn's per-page text (a chunk) can be verified as a (near-)verbatim substring of the independently-extracted raw page text. This catches LLM paraphrasing/hallucination during structuring without needing a human reviewer, and keeps the ground-truth layer (raw extracted text) untouched by the LLM. The raw per-page text is therefore persisted alongside the structured output, not discarded after structuring. A chunk that fails the check is **flagged in the stored JSON, not dropped or blocking** — the document is still stored, and the flag is left for the Analyzer/human reviewer to weigh.
- **Validation**: reusable plausibility-check assertions (e.g. non-empty participant list, turn count consistent with page count, every turn's speaker present in the participant list), used in two places: as pytest regression tests against the known fixture documents, and as pydantic validators enforced at runtime on every parse — a structurally implausible transcript should fail to construct rather than silently entering storage.

### Storage
- Prototype storage: pydantic-validated JSON files on disk, one per transcript, behind a thin storage interface. On-prem by default (no external dependency), trivially swappable for a real document database later without touching the pipeline or analyzer.

### Tech stack
- For required cloud services (e.g. Calling an LLM), we use Google Cloud Platform
- For the validation of data models and llm responses, we use pydantic
- Default LLM: Gemini via Vertex AI, called through a swappable wrapper (per the third-party-service requirement) — concrete model choice is a config detail, not a hard dependency of the design
- No retrieval/RAG for the prototype analyzer: the corpus is small (~19 documents, single-digit quarters per company) and each transcript fits comfortably in a long-context LLM call, so whole-transcript prompting is used directly. Flagged as a possible future extension if corpus size grows.
